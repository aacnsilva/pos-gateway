# Legacy fixed-width till format (layout 01)

| | |
| --- | --- |
| Media types | `text/x-fixed-width`, `text/plain` (a `charset` parameter is ignored) |
| Encoding | **ISO-8859-1 (Latin-1)**: one byte per character |
| Record length | **80 bytes**, excluding the line ending |
| Line endings | LF or CRLF |
| Adapter | `src/ingestion/adapters/fixed-width.adapter.ts` (`source.format = "fixed-width"`, `schemaVersion = "01"`) |
| Layout source | `src/ingestion/adapters/fixed-width.layout.ts` (the tables below are generated from it) |
| Fixtures | `fixtures/fixed-width/` (EV charging, parking with accents, shop with CRLF) |

## Why bytes and Latin-1

Column positions are **byte offsets**. In UTF-8, `é` takes 2 bytes, so a till that pads by bytes and a parser that counts characters disagree, and every field after the accent shifts by one, amounts included. Even "character" is ambiguous in Unicode: `é` can be one code point or two (`e` + combining accent), and JavaScript's `.length` counts UTF-16 units. ISO-8859-1 makes 1 byte = 1 character, so the positions can only mean one thing. The cost is that characters outside Western European scripts can't be represented, which is acceptable for till descriptions.

Measured cost of the alternative (UTF-8, NFC-normalised code points): about 4× slower to parse (≈100 µs vs ≈25 µs for a 50-line sale). That's irrelevant next to a database round trip, so the choice is about correctness, not speed.

## File structure

```
H   header         exactly one, first
L   line           one or more
P   payment        exactly one
T   trailer        exactly one, last; carries the line count and totals
```

The trailer's line count detects truncated files. Totals live in the trailer (as in most legacy batch formats) so a till can stream lines before knowing the total.

## Field rules

- **Text** fields are left-justified and padded with spaces on the right. Surrounding spaces are trimmed when read.
- **Numeric** fields are unsigned, zero-padded on the left, with no sign, decimal point or spaces: `000000045`.
- **Quantity** has **3 implied decimals**: `0000018500` = 18.500.
- **Money** is in minor units (cents) and gross (tax-inclusive). The till owns rounding: each `lineTotalMinor` must be within 1 cent of `quantity × unitPriceMinor`, and `totalMinor` must equal the sum of the line totals.
- **Timestamps** are UTC in the compact form `YYYYMMDDTHHMMSSZ` (`20261015T143000Z`). Local times aren't accepted.
- **Reserved** columns must be spaces. Non-blank filler almost always means the columns are shifted, and the error says so.
- **Control characters** (tabs included) aren't allowed anywhere in a record.

## Tolerated vs rejected

| Input | Result |
| --- | --- |
| CRLF or LF, with or without a final newline | accepted |
| Trailing blank lines | ignored |
| Spaces past column 80 | trimmed |
| Record shorter than 80 bytes (e.g. trailing spaces stripped by an editor) | rejected: padding can't be guessed back safely, because a truncated token would look valid |
| Non-space bytes past column 80 | rejected |
| A file that is valid UTF-8 with non-ASCII characters and the wrong record length | rejected with "looks UTF-8 encoded" |
| Blank line between records, unknown record type, wrong record order | rejected |

## Errors

Every error names the record number (1-based line in the file), record type and columns:

```json
{ "path": "record 2 [L] cols 44-53 quantity", "message": "must be 10 digits, zero-padded" }
```

Errors from the canonical checks (totals, currency, timestamps, tokens) are mapped back to the columns the till wrote. For example, a total that doesn't add up is reported at `record 4 [T] cols 6-16 totalMinor`, not at the canonical path `totalMinor`.

## Editing fixtures

Fixture files are byte-exact: `.gitattributes` stops git converting their line endings, and `.editorconfig` stops editors trimming trailing spaces or re-encoding them as UTF-8.
